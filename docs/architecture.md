# Architecture

For whoever inherits this. It explains what the pieces are, why they are that
way, and which decisions cost something to reverse.

Three companion documents: [`work-instructions.md`](./work-instructions.md) is
the shop's day-to-day procedures, [`handover.md`](./handover.md) is the transfer
runbook, and [`admin.md`](./admin.md) is the reference for the admin itself.

---

## In one paragraph

A vanilla JavaScript single-page site in `public/`, served by Cloudflare Workers
Static Assets, with a small Worker in front of it. The Worker serves the
photography out of an R2 bucket, answers four API routes, and hands everything
else to the static assets. The flooring catalogue is generated from supplier
photography by scripts in `tools/` and shipped with the site. Everything the
shop can change lives in one JSON document in the same bucket and is merged over
the catalogue in the browser at page load. There is no build step, no framework
and no `package.json`.

---

## Why there is no build step

The site is `<script src>` tags and plain functions. Nothing is compiled,
bundled or transpiled, and `git push` is the whole deployment.

This is a deliberate constraint, not an oversight, and it is worth keeping:

- **A carpet shop's website should still work in five years.** A toolchain is a
  thing that rots. A folder of `.js` files that a browser reads directly is not.
- **Anyone can open a file and read what the page does.** The next person to
  touch this may not be a front-end specialist.
- **Adding a `package.json` changes how Cloudflare builds it.** Workers Builds
  detects one and starts running an install and a build command. There is
  nothing for it to build, and it has broken the deploy before.

If a dependency ever becomes genuinely necessary, vendor the file into
`public/` rather than introducing a package manager.

## The request path

```
                    ┌──────────────────────────────────────────────┐
  browser  ────────▶│  Worker  (worker.js)  run_worker_first: true │
                    └───┬──────────────────────────────────────────┘
                        │
    /api/instagram  ────┼──▶ worker-instagram.js ──▶ Instagram Graph API
                        │                        └─▶ R2: cached feed + token
    /api/enquiry    ────┼──▶ worker-enquiry.js   ──▶ R2: admin/enquiries/
                        │
    /api/site       ────┼──▶ worker-admin.js     ──▶ R2: admin/site.json
    /api/admin/*    ────┤        (auth required)
                        │
    /assets/*.jpg   ────┼──▶ R2 bucket ──▶ (miss) ──▶ bundled copy
                        │
    everything else ────┴──▶ env.ASSETS  (the files in public/)
```

`run_worker_first: true` in `wrangler.jsonc` is load-bearing. Static assets are
normally served before the Worker runs at all, which would mean the photographs
bundled in `public/assets/` always won and R2 was never consulted.

**Ordering inside the Worker matters too.** `/api/instagram` and `/api/enquiry`
must be dispatched *before* `adminRoutes`, which answers 404 for anything under
`/api/` it does not recognise. A new route added after it looks exactly like a
route that was never built. `tools/worker.test.mjs` has a regression test for
this.

## The overlay: how the shop changes things without a deploy

This is the central idea. Get it wrong and everything else follows.

```
   public/data.js   CATALOGUE          generated by tools/, never hand-edited
        +
   R2  admin/site.json                 everything the shop has changed
        =
   RANGES + SITE in the browser        what a visitor actually sees
```

`applyOverlay()` in `public/app.js` merges them at page load. The overlay is
**fetched, never bundled**, so a change made in `/admin` is live in seconds with
no deploy.

Why it is built this way: the catalogue comes out of a pipeline that measures
colour from supplier swatch photographs — better data than anyone typing hex
codes, so it stays. But it runs when a supplier sends a new book, twice a year,
and the shop needs to change things weekly. Keeping the two apart means the
pipeline can regenerate whenever it likes without touching a word the shop has
written.

**A failure to load the overlay is silent on purpose.** The generated catalogue
ships with the site and is a complete, working shop on its own. If R2 is down,
`/api/site` 500s or the JSON is corrupt, the visitor gets the shipped site and
no error. `tools/admin-e2e.mjs` runs the whole suite against a deliberately
broken API to keep it that way — that is the single most important test here.

### What is in the document

| Key | What it holds |
|---|---|
| `content` | every word the shop has changed, keyed by name (`heroTitle`, `styleName-carpets-easy-clean`) |
| `off` | keys switched off entirely — `true` only. Blank and hidden are different intentions |
| `images` | which uploaded photograph is in which slot |
| `captions` | the alt text for each slot |
| `overrides` | collections and shades: hidden, renamed, re-described |
| `ranges` | whole collections added by hand |
| `extra` | shades added to a collection that came from the pipeline |
| `styles` | which collections sit under which style |
| `portfolio` | the jobs on the Portfolio page |
| `reviews`, `instagram` | the Google strip and hand-picked posts |
| `featured` | the collection pushed to the front |
| `version`, `updated` | optimistic concurrency — a save with a stale `baseVersion` is refused |

### Two kinds of name, and why they are not one thing

`worker-admin.js` validates with two different predicates, and conflating them
cost the shop every heading on the site for months:

```js
const SLUG = /^[a-z0-9][a-z0-9-]{0,63}$/;   // an id: a range, a style, a photo slot
const KEY  = /^[A-Za-z][A-Za-z0-9-]{0,63}$/; // a content key: a name in the code
```

Slugs come out of `slugify()` and the pipeline, are lowercase by construction,
and some of them **become R2 object keys** — that rule has to stay strict.
Content keys are camelCase names from the code. `isSlug` was applied to both, so
28 of the 44 admin boxes accepted text, reported "Saved", and were dropped here
on the way to R2. Neither regex allows a colon: colon is this document's
compound-key separator (`range:<id>`, `shade:<range>:<colour>`).

**Refusing is fine. Refusing quietly is not.** `clean(input, lost)` describes
everything it rejects into `lost`, and the PUT returns it as `dropped` for the
admin to display. This exists because the cap on added collections was 200, the
shop reached it, and every collection after that went in the bin behind a
"Saved" message. Any new rule added to `clean()` has to report its casualties
the same way.

**Nothing is ever deleted.** Saved shortlists and shared links reference a shade
by key, so deleting one would silently empty somebody's saved list. The admin
hides instead: the shade stops appearing, the link still resolves.

## Storage: one R2 bucket, four things in it

Bucket `haris-carpets`, bound as `PHOTOS`.

| Prefix | What it is | Written by |
|---|---|---|
| `assets/…` | all site photography, including per-shade swatches | `tools/sync-r2.py`, and the admin's uploads |
| `assets/uploads/…` | photographs uploaded through `/admin` | the admin API |
| `admin/site.json` | the overlay above | the admin API |
| `admin/enquiries/*.json` | one file per enquiry — **personal data** | the enquiry route |
| `admin/instagram-token.json`, `admin/instagram-feed.json` | the refreshed token and the last good feed | the weekly cron |

**`/assets/` is served `max-age=31536000, immutable`.** That is a year in every
cache between here and the customer, which is right for photography that never
changes — and a trap for anything that does. Every upload therefore gets a fresh
random filename rather than overwriting. Never "just replace the file".

The copies committed in `public/assets/` stay as a fallback: if R2 is
unreachable or an object is missing, the bundled file is served instead, so a
bucket problem degrades to slightly larger images rather than a site with no
photographs.

## The four routes

### `/api/site` — public, read-only
The overlay. Cached at the edge, `no-store` on the admin side of it. Serves an
empty document rather than an error if the stored one is unreadable.

### `/api/admin/*` — authenticated
Sign-in, the document, uploads, and the enquiry inbox. **Two ways in, and they
are alternatives rather than a fallback chain — if neither is configured, nobody
gets in.** An admin that opens up when its configuration is missing is worse
than one that never opens.

- **Cloudflare Access** — a code to Hari's email, no password to keep. The JWT
  is *verified* against Cloudflare's published keys, not trusted: a request that
  reached the Worker without passing through Access would otherwise be admitted
  on a header anyone can set.
- **A password** (`ADMIN_PASSWORD`) — signs a short-lived cookie. Needed because
  **Access can only guard hostnames in your own zones**, and `workers.dev` is
  Cloudflare's, not ours.

### `/api/instagram` — public
See the header comment in `worker-instagram.js`. The important part: a long-lived
token **expires after 60 days**, a cron refreshes it weekly, and the refreshed
token is written to R2 because *a Worker cannot write its own secrets*. The
secret is only the starting point. Failure degrades: live feed → last cached
feed → posts chosen by hand in `/admin` → the section does not render.

### `/api/admin/visitors` — authenticated
Cloudflare Web Analytics, read through their GraphQL API and rendered in the
admin so the shop needs no second login. Behind `identify()` with the enquiry
inbox. Off until four values are set, and it names the missing one rather than
showing an empty page. See `worker-analytics.js`.

### `/api/enquiry` — public, rate-limited
Writing the enquiry to `admin/enquiries/` **is** the delivery; it is then read on
the Enquiries tab. No third party is involved and there is no secret to set. If
`RESEND_KEY` is ever set the Worker also emails a copy, but the enquiry is stored
either way, so a failed send changes nothing the visitor sees.

Protection, sized for a shop that gets a few enquiries a week: a CSS-hidden
`website` honeypot (answered 200 and dropped — a 400 would teach the bot which
field to fix), a three-second minimum time-on-form, and two Workers rate-limit
bindings. Not a WAF rule: **WAF rate limiting is zone-scoped**, and this site is
on `workers.dev`.

## The wall this project keeps hitting

Three separate times, the Cloudflare feature we wanted turned out to require the
domain to be a **zone in the Cloudflare account**, and `haris-carpets.co.uk` is
at Wix:

1. **Access** cannot guard `workers.dev` → hence `ADMIN_PASSWORD`.
2. **WAF rate limiting** is zone-scoped → hence the rate-limit bindings.
3. **Email** — both the `send_email` binding and Email Service need the sending
   domain as a zone → hence no email at all, and the inbox instead.

All three become available on the day the domain moves. That single move is the
highest-value item on the list, and [`handover.md`](./handover.md) covers it.

## Scheduled work

Two cron triggers, told apart in `worker.js` by `event.cron`:

| Schedule | Does |
|---|---|
| `0 4 * * 1` (weekly) | refreshes the Instagram token and the cached feed. Weekly because a 60-day token gives five missed runs before anything breaks |
| `*/30 * * * *` | deletes enquiries past twelve months |

The twelve months is a promise made on `public/privacy.html`. **If that number
moves in `worker-enquiry.js`, it has to move on that page too, or the privacy
notice stops being true.**

## The catalogue pipeline

`tools/` turns a supplier's photo dump into `CATALOGUE` in `public/data.js`.
Full detail in [`photography.md`](./photography.md); the shape of it:

```
supplier dump in R2  ──▶ build-catalogue.py  ──▶ classify-tiles.py
                                              ──▶ emit-catalogue.py ──▶ public/data.js
                          sync-r2.py  optimises and uploads the photography
```

Two kinds of supplier image and they are not interchangeable: **colour chips**
are flat, evenly lit photographs of the physical swatch — the colour of those
pixels *is* the colour of the carpet, so every hex is measured rather than
invented — and **roomsets** are styled interiors, useful as pictures and useless
for colour. The pipeline never reads a colour from a roomset.

Colour *families* (the filter chips) are derived from the hex at runtime rather
than stored, so a new shade is filterable the moment it is added and there is no
label to keep in step with a swatch.

## The front end

| File | What it is |
|---|---|
| `public/index.html` | the shell: header, footer, and one `<main>` the router fills |
| `public/app.js` | routing, rendering, the overlay merge, favourites, the enquiry form |
| `public/data.js` | the generated catalogue plus every shipped default word and picture |
| `public/styles.css` | all of it |
| `public/visualiser.js` | the room visualiser (canvas, floor masks) |
| `public/admin/` | the admin, same style, no framework |
| `public/privacy.html`, `public/data-deletion.html` | **real files at real paths** — Meta and Google fetch a privacy URL without running JavaScript, so a hash route would hand them an empty page |

**The site makes no third-party request unless someone switches one on.** Fonts
come from Google, the map is an iframe on one page, and that is the lot — until
`ANALYTICS.token` in `data.js` is filled in, which loads the Cloudflare Web
Analytics beacon. That constant and the privacy page are checked against each
other in `smoke-test.mjs`: a token with no mention on the policy fails, and so
does a mention with no token.

Routing is hash-based (`#/collections/carpets`), which needs no server
configuration and cannot 404 on refresh.

### Two rules that are easy to break

**Everything the shop can change goes through `say()`.** Reading `CONTACT.hours`
or `st.name` directly is a value the shop cannot change — that is exactly how a
whole tab of the admin came to save happily and alter nothing. If you add
wording, add a key.

**A switched-off value must take its element with it.** `tag()`, `kicker()`,
`head()`, `para()` and `cta()` return an empty string rather than an empty
`<h2>`: an empty heading still takes space, still reads as a heading to a screen
reader, and still shows the rule above it.

## Testing

Six suites, no test framework — each one is a script that prints ticks and exits
non-zero. `tools/load-worker.mjs` loads the Worker without a bundler.

| Suite | Covers |
|---|---|
| `admin.test.mjs` | the admin API, with **real** RSA keys and real signed tokens: a forged signature, an expired token, a token for another application and the `alg:none` trick are all checked to fail |
| `enquiry.test.mjs` | the enquiry route — mostly by counting outbound calls, because a spam submission that answers 200 *and stores it* looks identical from outside to one that answers 200 and drops it |
| `instagram.test.mjs` | the feed, the token expiring, and that the token never appears in a response |
| `worker.test.mjs` | routing and the R2 photo route |
| `analytics.test.mjs` | visitor numbers, and every way they can fail — a refused query, an unreachable API, nothing configured |
| `admin-e2e.mjs` | the admin in a real browser, against `tools/stub-api.mjs` |
| `smoke-test.mjs` | the public site against a plain file server with **no API at all** |

Two of these are worth defending:

**The shop survives a broken API** (`admin-e2e.mjs`). With the admin API
returning 500, the site still renders its full catalogue with no errors.

**The field sweep** (same file). It types a unique marker into *every* box in the
admin, saves, reads back every public page, and fails naming any box whose marker
never appeared — 88 boxes at the time of writing. This is the check that a box
does something, and it only became one recently: `tools/stub-api.mjs` used to
echo the posted document straight back, which proved only that the *browser* sent
the value. It runs the real `clean()` now, so the stub and the Worker cannot
disagree about what survives a save.

How to run them: see the Tests section of [`admin.md`](./admin.md).

## Things that will bite

- **A Worker cannot see a secret added since its last deploy.** Add the secret,
  then redeploy. This has cost real hours on `ADMIN_PASSWORD` and again on
  `INSTAGRAM_TOKEN`.
- **`/assets/` is immutable for a year.** Fresh filenames, always.
- **A stored Instagram token shadows the secret.** The R2 copy is preferred, so
  putting a new token in as a secret does nothing until the stored one fails —
  `worker-instagram.js` now tries both, but know that it works this way.
- **Google Fonts is unreachable from some sandboxes**, and a request that never
  settles makes Playwright's `networkidle` hang until the run is killed. The
  test suites block it.
- **The shop's saved text always beats a shipped default.** Changing a default in
  `data.js` does nothing on a page where somebody has typed into that box.
  Clearing the box in `/admin` restores the shipped wording.
- **Two similar domains.** The mailbox is `sales@hariscarpets.co.uk`, no hyphen.
  The website is `haris-carpets.co.uk`, with one. Verifying one does not
  authenticate the other.
